# Руководство по структурированной разработке ПО с ИИ-агентами (Вайбкодинг без техдолга)

> **Аннотация:** Это подробное руководство описывает методологию работы с ИИ-агентами при разработке программного обеспечения, позволяющую избежать хаотичного редактирования, бесконечных исчислений ошибок и накопления скрытого технического долга.

---

## 1. Проблема «наивного» вайбкодинга

Большинство начинающих разработчиков при работе с ИИ попадают в замкнутый круг:

```
[Промпт] ➔ [Получение кода] ➔ [Возникновение ошибки] ➔ [Промпт на исправление] ➔ (Повтор)
```

### Основные недостатки хаотичного подхода:
1. **Иллюзия быстрого прогресса:** На простых задачах кажется, что приложение пишется мгновенно, но с ростом сложности проект становится нестабильным.
2. **Потеря контекста:** При больших объемах кода ИИ-агент забывает ранее принятые архитектурные решения.
3. **Рост технического долга:** Исправление одной ошибки часто приводит к появлению нескольких новых в других частях системы.

---

## 2. Этап 1: Обсуждение задачи и брейншторминг

Любой проект должен начинаться с фазы исследования и ликвидации «белых пятен».

* **Интервью с ИИ:** Попросите агента провести с вами интервью и вытянуть из вас все ключевые детали проекта.
* **Использование специализированных скилов:** Применяйте специализированные промпты или скилы (например, *Brainstorming*, *Grill me*).
* **Сферы обсуждения:**
  * Потребности пользователей и бизнес-логика.
  * Архитектура системы.
  * Выбор оптимального технологического стека.

---

## 3. Этап 2: Двухуровневое специфицирование

Чтобы обезопасить проект от искажения первоначального замысла, требования разделяются на два документа.

### 1. Technical Specification (Tech Spec) — для ИИ-агента
* **Назначение:** Единый источник правды (*Source of Truth*) о технической устройстве системы.
* **Содержание:** Архитектура, структура базы данных, схемы API, описание функций и взаимодействия компонентов.
* **Правило актуализации:** В правила агента обязана входить инструкция: *при любом изменении логики Tech Spec должна мгновенно обновляться*.

### 2. Product Specification (Product Spec) — для человека
* **Назначение:** Контроль функциональности человеком-разработчиком.
* **Содержание:** Поведение приложения с точки зрения пользователя простым языком, без технических терминов.
* **Правило проверки:** Разработчик **обязан лично вычитать** Product Spec, так как ошибки в продуктовой логике перейдут на все последующие этапы разработки.

---

## 4. Этап 3: Пошаговое планирование и критерии приёмки

```
[Спецификация] ➔ [Детализированные планы этапов] ➔ [Консультация с MCP] ➔ [Критерии приёмки]
```

1. **Разбиение на этапы:** Каждая задача разбивается на конкретные технические планы с указанием задействованных файлов, функций и сторонних API.
2. **Проверка актуальной документации (MCP Context Server):** Перед планированием и написанием кода ИИ-агент обязан свериться с актуальной документацией библиотек через MCP. Это исключает использование устаревших методов из обучающей выборки.
3. **Формулирование критериев приёмки (Acceptance Criteria):** Определение четких, объективно проверяемых условий выполнения задачи (например, «при успешной оплате пользователь моментально получает доступ, повторные запросы не ломают сценарий»).

---

## 5. Этап 4: Разработка через тестирование (TDD)

Написание автотестов **строго предшествует** написанию логики приложения.

### Цикл TDD для ИИ:
1. **Создание теста:** Агент пишет скрипт для проверки конкретного функционала.
2. **Проверка падения («красный» тест):** Запуск теста подтверждает, что он падает (так как целевой код ещё не написан).
3. **Написание кода:** Агент создает функционал до момента, пока тест не станет «зеленым».

> **Важно:** Если писать тесты после кода, ИИ неизбежно подгонит их под готовую реализацию, сделав тестирование необъективным. TDD также защищает проект от **регрессионных ошибок** (когда новый код ломает старый).

---

## 6. Этап 5: Браузерное тестирование, негативные сценарии и безопасность

Код под капотом может работать корректно, но пользовательский интерфейс в браузере при этом может быть сломан.

### 1. Формирование тест-кейсов (QA-подход)
Для каждого раздела формируются два типа сценариев:
* **Позитивные:** Идеальное поведение пользователя (ввод верных данных, корректные клики).
* **Негативные:** Ошибки и нестандартные действия (ввод некорректного email без `@`, пароли из 1000 символов, пустое поле).

### 2. Автоматизация через Playwright MCP
ИИ-агент запускает сценарии в реальном браузере с помощью Playwright MCP, эмулируя действия человека (клики, заполнение форм, навигацию).

### 3. Проверка безопасности (Security Review)
Перед релизом модулей авторизации, платежей или работы с персональными данными проводится специальный аудит безопасности.

## 7. Этап 6: Система контроля версий (Git), Worktrees и Staging

| Инструмент / Метод | Назначение |
| :--- | :--- |
| **Git** | Фиксация истории изменений, быстрый откат к стабильным версиям, разработка фич в изолированных ветках. |
| **Git Worktrees** | Разделение работы нескольких ИИ-агентов по отдельным директориям с последующим сведением кода и разрешением мерж-конфликтов. |
| **Staging** | Изолированное тестовое окружение (копия продакшена) для итоговой проверки перед выпуском для пользователей. |

> **Принцип доказательности:** Заявления ИИ «всё готово» не являются аргументом. Доказательством выполнения задачи считаются только **зеленые автотесты**, пройденные **браузерные тест-кейсы** и соответствие **критериям приёмки**.

---

## 8. Защита от контекстного хаоса и скрытого техдолга

На масштабных проектах ИИ-агенты склонны принимать несанкционированные решения или откладывать задачи «на потом». Чтобы этого избежать, внедряются дополнительные инструменты:

* **Журнал принятых решений (Decision Log):** Файл, в котором ИИ фиксирует каждое принятое техническое решение, альтернативы и возможные последствия.
* **Карта кода (Code Map):** Структурированный Markdown-документ или граф через MCP, описывающий устройство модулей и их взаимосвязи. Не позволяет агенту «изобретать велосипеды».
* **Запрет на самостоятельный техдолг:** Агенту строго запрещено откладывать задачи или менять архитектуру без явного согласования с человеком.

---

## 9. Бизнес-аспект: Лидогенерация и продажи

Создание качественного ПО — это лишь половина успеха. Для коммерческого существования проекта или фриланс-практики необходимо:
1. Параллельно с разработкой выстраивать портфолио.
2. Настраивать регулярную систему привлечения клиентов (лидогенерацию).
3. Погружаться в глубокую разработку только после того, как процесс поиска заказов запущен.

## 10. Полезные плагины и скилы

Инструменты ниже не обязательны — методология из разделов 1–9 работает и без них. Это конкретные реализации, закрывающие отдельные этапы.

| Этап | Инструмент | Что закрывает | Ссылка |
| :--- | :--- | :--- | :--- |
| 1 | *Brainstorming* (Superpowers) | Уточнение идеи через вопросы до написания кода | <https://github.com/obra/superpowers> |
| 1 | *Grill me* | Допрос по плану до закрытия каждой ветки решений | <https://github.com/mattpocock/skills> |
| 2 | *Domain Modeling*, *to-spec* | Ведение `GLOSSARY.md` и ADR, синтез спеки | <https://github.com/mattpocock/skills> |
| 3 | *Writing Plans*, *to-tickets* | Дробление плана на задачи с зависимостями | <https://github.com/obra/superpowers> |
| 3 | Context7 (MCP) | Актуальная документация библиотек вместо памяти модели | <https://github.com/upstash/context7> |
| 4 | *TDD* | Цикл red-green-refactor по вертикальным срезам | <https://github.com/mattpocock/skills> |
| 5 | Playwright (MCP или CLI) | Браузерные тест-кейсы на реальном приложении | <https://github.com/microsoft/playwright-mcp> |
| 5 | *Security Review* | Аудит безопасности (STRIDE) перед релизом | скилл агента |
| 6 | *Using Git Worktrees* | Изолированные рабочие копии для параллельных агентов | <https://github.com/obra/superpowers> |
| 7 | *Verification Before Completion* | Запрет объявлять «готово» без вывода проверок | <https://github.com/obra/superpowers> |

**Superpowers** — методология целиком: 14 скиллов, срабатывающих автоматически перед каждой задачей. Ставится плагином в OpenCode, Claude Code, Codex, Cursor и другие агенты; инструкция по установке — в репозитории проекта.

**Skills for Real Engineers** — коллекция скиллов Мэтта Покока. Важное отличие: скиллы разделены на *user-invoked* (срабатывают только по команде, например `/grill-me`) и *model-invoked* (агент берёт сам). Поэтому «поставил скилл — заработало» верно не для всех.

**Context7** работает в двух режимах — CLI со скиллом или MCP-сервер. Нужен не только при планировании, но и при любой работе с API библиотек: модель по памяти предлагает методы, которых в реальной версии уже нет.

**Playwright** поставляется как MCP-сервер, но для кодовых агентов сами разработчики рекомендуют CLI-вариант: MCP загружает в контекст большие схемы инструментов и деревья доступности, что заметно дороже по токенам.
